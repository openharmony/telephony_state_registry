## 快速分诊表

| 现象 | 首查位置 | 对应失效模式 |
|---|---|---|
| 服务进程崩溃，栈在 map 或 vector 迭代中 | 服务侧缓存成员的读点 | 「未持锁的读」 |
| 查询接口偶发返回异常值 | `GetXxx` 系列 | 「未持锁的读」 |
| 服务后台线程或延迟任务崩溃在成员函数上 | 异步体的捕获列表 | 「异步体持有悬空 this」 |
| JS 回调在某条错误日志后长时间不再触发，或 `on`/`off` 阻塞 | napi 中接收 `unique_lock &` 的函数 | 「锁传递契约被打破」 |
| 订阅后应用进程内存持续增长 | 前端 `HandleCallbackInfoUpdate` 与 `WorkXxxUpdated` | 「回调负载所有权错乱」 |
| 前端偶发崩溃在释放语句 | 同上 | 「回调负载所有权错乱」 |
| 系统部件注册或注销时进程挂起 | 观察者回调路径 | 「回调中重入服务锁」 |
| 注册返回成功但收不到回调 | 卡槽号、多卡能力、权限日志 | 「静默成功分支」 |
| 某一种应用框架正常，另一种异常 | 三套前端的对应实现 | 「前端不同步」 |
| 两个部件升级后回调错乱 | 接口码与掩码 | 「跨仓定义不同步」 |

## 失效模式

### 未持锁的读

**机制：** 写路径持有 `lock_`，但某个读路径没有持锁。`std::map` 的插入会重排节点，与并发遍历交错时读到已释放的节点。

**识别：** 读路径是查询接口、dump、补发（`UpdateData`）这类「看起来只读」的函数。

**修复：** 在读路径加 `std::shared_lock<std::shared_mutex>`，范围覆盖整个遍历。按成员名全文搜索，同一模式的所有读点一并修复，并在回复中列出清单。

### 异步体持有悬空 this

**机制：** `std::thread(...).detach()`、延迟任务、回调中使用 `this` 或 `[&]`。异步体执行时服务对象已销毁或重建。

**识别：** 崩溃线程是服务自己创建的线程或任务，栈顶是服务成员函数。

**修复：** 捕获 `weak_from_this()`，执行时 `lock()` 判空；成员值拷贝为局部变量按值捕获。

### 锁传递契约被打破

**机制：** 锁以 `std::unique_lock &` 传入，正常路径在调用 JS 前释放，但提前返回路径没有释放。锁在后续处理期间一直被持有，与正常路径的约定不一致；如果调用方或后续逻辑按「已释放」处理，就会出现等待、重入死锁或监听表操作被阻塞。

**等待方：** 锁被持有期间，`EventListenerHandler` 事件线程上的 `HandleCallbackInfoUpdate`、`HandleCallbackVoidUpdate`，以及 JS 线程上的 `on`、`off`，都在 `operatorMutex_` 上等待；同一 JS 线程在此期间重入 `on`、`off` 会死锁。

**识别：** 错误日志出现在提前返回分支（句柄作用域、回调引用、回调函数为空等），之后同一进程的回调或 `on`/`off` 表现异常。

**修复：** 在每条提前返回路径上补 `lock.unlock()`，与正常路径对齐。检查同文件中所有接收该锁的函数。

### 回调负载所有权错乱

**机制：** 负载的分配方与释放方约定不一致。常见形态：

- 被调函数用 `std::unique_ptr` 接管，但在接管之前的提前返回路径上负载无人释放。
- 分发方以为被调方会释放，被调方在丢弃分支（监听已删除、事件类型未知）直接返回。
- 同步分发的一方沿用了异步分发的「转交所有权」写法。

**识别：** 应用长时间订阅高频事件（信号、网络状态）后内存增长；增长速度与事件频率相关。

**修复：** 先确定该前端是同步还是异步分发，再按「回调负载的所有权」中的约定统一：同步分发由分配方在分发返回后释放，被调方只借用；异步分发由接收方接管，丢弃分支同样释放。

### 回调中重入服务锁

**机制：** 服务在共享锁内调用观察者，同进程观察者在回调中同步调用注册或注销，等待独占锁，而共享锁由同一线程持有。

**修复：** 观察者侧把重入操作投递到其他线程执行；服务侧不要把回调移到独占锁内。

### 静默成功分支

**机制：** `RegisterStateChange` 在多卡能力不支持或卡槽越界时返回成功但不写入注册表。

**修复：** 这是已发布行为，修复点在调用方传入的卡槽号。若确需改为报错，属于需要人工确认的改动。

### 前端不同步

**机制：** 事件类型或回调字段只在一套前端中实现或修复。

**修复：** 修复任一前端时，列出另外两套中的对应函数并逐一核对同类问题。

### 跨仓定义不同步

**机制：** core_service 仓的接口码或掩码与本仓的处理不一致，Stub 按错误的接口码分发。

**修复：** 接口码只追加，两仓同步提交，属于需要人工确认的改动。

## 根因排查方法

- **从日志文本反查位置。** 前端与服务的错误日志文本在仓内基本唯一，先用全文搜索定位分支。
- **按契约判断，不按多数判断。** 同族函数（十余个 `WorkXxxUpdated`、七个 `GetXxx`）写法一致不等于正确。先写出该族函数应遵守的契约（持锁、释放、所有权），再逐个核对；多数一致而少数不同时，要分别判断哪一方违反契约。
- **一个现象对应一条机制。** 每个现象都要找到能解释「为什么是这个表现」的具体路径；解释不了表现的候选根因，即使代码确实有瑕疵，也不要作为该现象的结论，单独记为技术债。
- **沿所有退出路径追踪。** 锁和内存问题都出在少走的分支上，逐个列出 `return`。

## 修复反例

| 反例 | 问题 | 正确做法 |
|---|---|---|
| 为读路径拷贝一份缓存副本来避免加锁 | 拷贝本身仍在无锁读 | 加共享锁 |
| 把观察者回调整体放进独占锁 | 放大锁范围，回调重入时死锁 | 保持「独占写、共享遍历」 |
| 异步体改为按值捕获 `this` | 仍是裸指针 | 捕获弱引用 |
| 在提前返回路径上关闭从未成功打开的句柄作用域 | 作用域不配对 | 打开失败直接释放锁返回 |
| 在调用方与被调方都加释放语句 | 重复释放 | 确定唯一所有者 |
| 只修复现象中点名的几个函数 | 同族函数残留同一缺陷 | 按成员或契约全量搜索 |

## 回归要求

| 改动类型 | 回归 |
|---|---|
| 服务侧加锁 | `tel_state_registry_test` 与 `tel_state_registry_branch_test` 全绿；说明读写交错场景 |
| 生命周期 | 用例覆盖服务对象释放后异步体不执行成员调用的路径，或在回复中说明验证方式 |
| napi 锁与句柄 | 无单测，设备上验证：订阅高频事件，在回调中调用 `off` 再 `on`，确认无阻塞 |
| 前端内存 | 设备上长时间订阅信号与网络事件，对比进程内存趋势 |
| 权限 | `tel_state_registry_branch_test` 通过替身构造权限拒绝 |
